## Preconditions
A playlist resolves to music metadata.

## Main Flow
1. The user views a playlist.
2. Maple Pod derives available non-empty marks from resolvable tracks in that playlist.
3. The user selects zero or more marks to narrow the visible tracks.
4. Multiple selected marks combine with OR semantics; selecting no marks shows every resolvable track.
5. The active mark filter belongs only to the current playlist view and is cleared when leaving that playlist context or reloading the application.
6. A locate action can navigate to a target playlist containing a known music item and reveal that item in playlist context without changing playlist membership.

## Alternate & Failure Flows
- A selected mark set with no matching tracks produces a distinguishable no-results state rather than redefining the playlist as empty.
- If the requested playlist or music membership cannot be resolved, the locate action produces no membership side effect.
- If an active filter would hide the located track, a successful locate action must override or adjust presentation sufficiently to reveal that target; the exact UI mechanism is not normative.

## Observable Outcomes
Filtering changes only presentation for the current playlist view and does not persist across playlist changes or reloads. A successful locate action leaves membership/order unchanged and makes the requested music visibly reachable in the target playlist context.

## Reverse-spec evidence
Observed in `src/views/Playlist.vue`, `src/components/PlaylistFilterDropdown.vue`, `src/components/MusicDropdownMenu.vue`, and `src/composables/useAppStore.ts`. Product review explicitly accepted playlist-derived non-empty marks, OR multi-select semantics, no-selection = all, ephemeral filter lifetime, and track location with a required reveal outcome. The reveal guarantee is normative even if current scrolling/filter interaction needs implementation adjustment.
