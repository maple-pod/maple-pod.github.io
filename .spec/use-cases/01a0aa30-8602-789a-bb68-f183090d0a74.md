## Preconditions
The browser supports service workers and Maple Pod can register its PWA worker.

## Main Flow
1. Maple Pod registers its service worker and prepares an application shell/runtime cache sufficient for supported generic offline reuse.
2. When that generic app-shell offline capability becomes ready, Maple Pod exposes a user-visible offline-ready notice.
3. When a newer deployed application version becomes available through the service worker update lifecycle, Maple Pod exposes a user-visible update-ready state.
4. The current page/session continues running until the user explicitly chooses Reload.
5. Choosing Reload applies the available update and reloads the page into the newer application version.
6. Dismissing/closing the notice does not itself force the update reload.

## Alternate & Failure Flows
- If service workers are unsupported or unavailable, Maple Pod remains usable as an ordinary web app without PWA-specific guarantees.
- Generic service-worker cache readiness must not be interpreted as Music or World Map explicit offline readiness.
- Cached runtime resources may support useful degraded behavior, but they must not bypass the stricter per-capability offline contracts.

## Observable Outcomes
On supported browsers, the user can see when the app shell is ready for generic offline reuse, can see when an update is available, and retains control over when the disruptive reload occurs. Music/World Map offline-ready state remains independently determined by their own download/verification contracts.

## Reverse-spec evidence
Observed in `vite.config.ts` and `src/components/PwaReloadPrompt.vue`. Product review explicitly accepted the visible offline-ready/update-ready states and explicit Reload boundary while leaving cache strategy details non-normative.
