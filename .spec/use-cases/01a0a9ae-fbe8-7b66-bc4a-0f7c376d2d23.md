## Preconditions
The sender has a resolvable music item or a saveable Liked/custom playlist. The receiver opens a Maple Pod sharing URL and application data becomes ready.

## Main Flow
1. The sender copies a Maple Pod music or playlist sharing link.
2. A music link uses `/play/?musicId=...`; Maple Pod resolves the referenced music and asks the receiver for confirmation before starting playback from All.
3. A playlist link uses `/import-playlist` with a compressed serialized playlist payload in the URL hash.
4. The playlist payload identifies the `import-saveable-playlist` action and carries playlist kind, title, and an ordered list of music IDs. Liked and custom playlists are shareable; All is not.
5. Maple Pod decodes and validates the payload and resolves each referenced music ID against the receiver's current catalog.
6. If every music ID resolves, Maple Pod asks the receiver for confirmation and, if accepted, opens a prefilled playlist-creation flow.
7. If one or more music IDs do not resolve, Maple Pod discloses the unresolved items and asks whether the receiver accepts importing only the resolvable subset. Only explicit acceptance may continue with that reduced ordered list.
8. The receiver completes or cancels the prefilled creation flow.
9. Each route returns the receiver to the normal application flow after handling the action.

## Alternate & Failure Flows
- Unknown music IDs in a music share do not start playback.
- Playlist hashes that cannot be decoded, have the wrong action type, or fail schema validation are rejected.
- If unresolved playlist music exists and the receiver does not explicitly accept dropping it, no playlist import proceeds.
- Declining sharing confirmation prevents either shared action from proceeding.
- Cancelling the prefilled playlist-creation flow creates no playlist.
- Partial playlist import is allowed only after unresolved items have been disclosed and the receiver explicitly consents to discarding them.

## Observable Outcomes
A valid, confirmed music link starts the referenced music. A valid playlist link with fully resolvable music opens playlist creation after confirmation. A playlist link containing unresolved music first surfaces the unresolved items; if the receiver explicitly accepts the reduced import, playlist creation opens pre-populated with only the resolvable music in their original relative order. Rejected, malformed, unknown, or unconfirmed input produces no shared-action side effect.

Observed in `src/router/index.ts`, `src/components/PlaylistDropdownMenu.vue`, `src/components/MusicDropdownMenu.vue`, `src/components/CreatePlaylistDialog.vue`, `src/schemas/HashActionImportSaveablePlaylistData.ts`, `src/schemas/SaveablePlaylist.ts`, and `src/utils/common.ts`. The common Story scope, mandatory receiver confirmation, current sharing transport protocol, shareable playlist kinds, semantic payload fields, prefilled creation flow, and unresolved-music disclosure/consent behavior were explicitly confirmed during reverse-spec review. The current route does not yet implement per-music resolution or the disclosure/consent branch, so this accepted behavior represents normative intent rather than observed implementation.
