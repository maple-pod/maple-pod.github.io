## Legacy Feature notes

## Capability
Provide a coherent queue-based listening session for a selected playlist.

## Semantics
A session has a source playlist, an ordered set of candidate music, and at most one established current track. Selection and navigation consume playability as an input. Playback preferences are durable user preferences, while the live queue and current position belong to the active session.

## Rules
- A requested starting item must belong to the selected playlist.
- Unavailable candidates are not intentionally selected during initialization or navigation.
- Random and repeat behavior change selection within the same session without creating a second playback context.
- Previous, seek, and repeat boundary behavior follows the Playback contract.
- A candidate becomes current only after the playback transition succeeds.
- Preference persistence must not imply persistence of the live queue or current position.

## Edge Cases
Empty or wholly unavailable playlists, stale identifiers, asynchronous source changes, seek boundaries, and failed source transitions must not establish an invalid current track.

## Legacy Requirement notes: Playback queue and control behavior

## Contract
When playback is requested for a valid playlist, Maple Pod must select only a music ID contained in that playlist and must skip items currently unavailable for playback. The playback contract consumes item playability as an input and does not define the connectivity or offline rules that determine it.

The session must expose pause/resume, seek within the current track, next, previous, random, volume, mute/unmute, and `off` / `repeat` / `repeat-1` repeat controls. Previous must restart the current music when playback has progressed beyond three seconds; at three seconds or less it must navigate backward in the queue.

Changing random, repeat, volume, or muted state must update active playback behavior and persist the resulting preference across reloads. Persisting current track, queue position, or elapsed playback time across reloads is not required by this contract.

A requested item must not become the current track unless its source resolves and playback starts successfully. Source-resolution or playback failure must leave the session without a successful transition to that item.

## Rationale
The contract separates playback semantics from the policy that decides whether a music item is playable. This keeps offline/connectivity policy independently evolvable while guaranteeing that the queue never intentionally selects an unavailable item.

## Verification
Exercise playback from a playlist containing both playable and unavailable items; verify requested-item membership checks and skip behavior. Verify seek, next, previous on both sides of the three-second threshold, random toggling, all repeat modes, volume adjustment, and mute/unmute. Reload the application and verify random, repeat, volume, and muted preferences persist. Force source-resolution and playback failures and verify the failed candidate does not become the successfully established current track.
