## Legacy Feature notes

## Capability
Automatically compensate playback loudness when current, complete analysis and a safe output path are available.

## Semantics
Loudness normalization is a Playback capability with build-wide report eligibility and a fixed gain policy defined by its normative contract. It applies per track only when the report represents the current catalog and the output can safely apply the policy. Normalization is subordinate to ordinary playability.

## Rules
- Report eligibility is all-or-nothing for the current resource build.
- Eligible measurements are constrained by the accepted target and peak-safety policy.
- Missing measurements, ineligible reports, unsupported output, and normalization failure result in ordinary playback without compensation.
- Normalization failure cannot make a playable track unavailable.

## Edge Cases
A peak constraint may limit compensation below the loudness target. A track may require negative gain. A report that is valid for another catalog build cannot partially normalize the current catalog.

## Legacy Requirement notes: Loudness-normalization eligibility and fallback behavior

## Contract
Maple Pod must provide automatic playback loudness normalization when, and only when, both an eligible loudness-analysis report and a capable output path are available.

A loudness report is eligible only if all of the following are true: `failureCount === 0`; `successCount` equals the current music catalog size; `trackCount` equals the current music catalog size; and `resourceBuiltAt` exactly matches the current resource build. If any condition fails, the report must be treated as ineligible as a whole. Maple Pod must not apply measurements selectively from a partial, failed, stale, or differently built report.

For an eligible track measurement, the normative gain policy is:
- integrated loudness target: -16 LUFS;
- true-peak ceiling: -1 dBTP;
- target gain = `-16 - integratedLufs` dB;
- peak-safe gain = `-1 - truePeakDbtp` dB;
- applied normalization gain = the smaller of target gain and peak-safe gain.

When the playback output can safely apply normalization, Maple Pod must automatically apply that per-track gain.

If the report is missing/ineligible, a track lacks usable measurement data, the normalization output path is unsupported, or the normalization subsystem fails, Maple Pod must bypass normalization and keep ordinary playback usable. Normalization failure must not make an otherwise playable track unavailable and must not block normal playback.

## Rationale
The feature exists to reduce track-to-track loudness variation while avoiding peak overshoot. Strict build-wide eligibility prevents mixing measurements with a different catalog revision or silently producing inconsistent loudness across only a subset of tracks. Safe bypass keeps normalization subordinate to the primary goal of reliable BGM playback.

## Verification
Test a fully matching report and confirm normalization activates. Independently alter `failureCount`, `successCount`, `trackCount`, and `resourceBuiltAt` and confirm the entire report is rejected. Verify gain calculations around both the -16 LUFS target and -1 dBTP ceiling, including cases where the peak ceiling is the limiting factor. Test a missing report, unsupported normalization output, normalization-output failure, and ordinary-playback fallback; in every unavailable or failed-normalization case, verify playback remains usable with normalization bypassed.
