## Capability
Automatically normalize playback loudness using a complete, current-build loudness-analysis report when the playback output can safely apply per-track gain.

## Semantics
Loudness normalization is a formal Playback capability rather than an optional implementation optimization. Eligibility is strict and all-or-nothing for the report: zero failures, report success/track counts exactly equal to the current catalog size, and exact `resourceBuiltAt` match are all required. Eligible tracks use a fixed target of -16 LUFS and a true-peak ceiling of -1 dBTP; applied gain is constrained by whichever limit is stricter. If normalization cannot be used, playback must safely bypass it without becoming unavailable.

## Rules
- Normalization is automatic when both a complete matching report and a supporting output path are available.
- Report `failureCount` must be zero.
- Report `successCount` and `trackCount` must each equal the current catalog track count.
- Report `resourceBuiltAt` must exactly match the current resource build.
- Partial per-track normalization from an otherwise incomplete/mismatched report is not permitted.
- Normalization target is -16 LUFS integrated loudness.
- True-peak ceiling is -1 dBTP.
- Applied gain is `min(target gain, peak-safe gain)`.
- Missing/ineligible measurements or unsupported/failed enhanced output must result in zero normalization gain/bypass, not playback failure.

## Edge Cases
A track that would need positive gain to reach -16 LUFS may receive less gain when its true peak would otherwise exceed -1 dBTP. A track louder than target may receive negative gain. If the normalization output path fails after playback has become available, Maple Pod must fall back to ordinary playback rather than muting, blocking, or invalidating the track. Report eligibility is tied to the complete current catalog/build, not individual-track availability.

## Reverse-spec evidence
Observed in the music-store loudness loader, loudness gain utility, audio-output graph, and playback backend. The accepted numeric target/ceiling and strict report gate intentionally make these behaviors normative and testable.
