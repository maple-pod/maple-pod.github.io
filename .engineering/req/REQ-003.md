## Requirement

The music player exposes the standard transport and playback controls: play/pause, previous/next track, a seekable progress bar with elapsed/total time, a volume slider with mute toggle, a shuffle (random) toggle, and a repeat control cycling through `off`, `repeat` (loop queue), and `repeat-1` (loop current track). Control state is reflected in the UI and integrated with the browser Media Session where available.

`HTMLAudioElement` remains the authoritative playback primitive regardless of whether output is native or Web Audio-enhanced. For validated MSE-compatible WebM/Opus tracks, logical track changes must preserve one `HTMLAudioElement` and one `MediaSource` object URL; the player maps the global MSE media clock to the current track's local elapsed time and duration. Unsupported representations may use direct media-element source replacement as a compatibility fallback, and any such replacement must explicitly request playback rather than depend on `autoplay`. Output enhancement must not be required for media time to advance or for the queue to continue.

## Rationale

These are the controls users expect from any music player; without them the app is a demo, not a player. The three-state repeat and shuffle mirror common player semantics. Keeping the media element authoritative also allows browser-native background playback to continue when optional processing infrastructure is interrupted.

## Acceptance Criteria

- Play/pause, previous, and next act on the current queue.
- Dragging or clicking the progress bar seeks within the current track.
- Volume changes take effect immediately; mute preserves the previous volume.
- Toggling random reshuffles the queue order; toggling it off restores list order.
- Repeat cycles off → repeat → repeat-1; `repeat` continues past the queue end, `repeat-1` replays the current track, `off` stops at the queue end.
- Player control preferences (volume, muted, random, repeated) persist per REQ-006.
- Validated MSE-compatible track changes preserve the same media element and `MediaSource` object URL across natural transitions, next/previous, queue navigation, and queue reorder/shuffle reconciliation. Direct-source fallback transitions explicitly request playback instead of relying on `autoplay`; a rejected playback request is observable and does not leave transition output muted.
- Hidden pages and non-running Web Audio contexts route active playback through the native media-element output without replacing/reloading the current source or transferring playback position.
- Foreground recovery switches back to enhanced output only after the Web Audio context is confirmed running; a blocked resume leaves native playback active.
- A browser without the required Web Audio/capture capability continues through native media-element playback without creating a partial enhancement dependency.
- While the Android native-only reliability baseline is active, Android playback does not create `captureStream()` or `AudioContext` dependencies in either foreground or background playback.
- Media Session transport and seek actions operate on logical current-track time even when the underlying media element clock spans a longer MSE timeline.
- On the Android native-only diagnostic baseline, track switching does not intentionally drive the authoritative media element's native output volume to zero before replacing the source.
