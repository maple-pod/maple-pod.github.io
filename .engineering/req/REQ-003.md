## Requirement

The music player exposes the standard transport and playback controls: play/pause, previous/next track, a seekable progress bar with elapsed/total time, a volume slider with mute toggle, a shuffle (random) toggle, and a repeat control cycling through `off`, `repeat` (loop queue), and `repeat-1` (loop current track). Control state is reflected in the UI and integrated with the browser Media Session where available. When active playback changes media source, the player must explicitly request playback of the replacement source rather than depend on the media element's `autoplay` behavior, including while the page is backgrounded when the browser and operating system permit background media playback.

## Rationale

These are the controls users expect from any music player; without them the app is a demo, not a player. The three-state repeat and shuffle mirror common player semantics.

## Acceptance Criteria

- Play/pause, previous, and next act on the current queue.
- Dragging or clicking the progress bar seeks within the current track.
- Volume changes take effect immediately; mute preserves the previous volume.
- Toggling random reshuffles the queue order; toggling it off restores list order.
- Repeat cycles off → repeat → repeat-1; `repeat` continues past the queue end, `repeat-1` replays the current track, `off` stops at the queue end.
- Player control preferences (volume, muted, random, repeated) persist per REQ-006.
- Natural and explicit track changes request playback of the replacement source explicitly instead of relying on `autoplay`; a rejected playback request is observable and does not leave the transition output muted.
- If the Web Audio context becomes recoverably non-running while the media element remains actively playing, the player attempts to resume it without replacing or reloading the current media source.
- Media Session transport actions continue to operate through the same explicit playback path.
