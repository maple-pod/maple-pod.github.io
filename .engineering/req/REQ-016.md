## Requirement

The World Map must load its snapshot catalog from `/resources/world-map/catalog.json` and expose only catalog entries with `selectable: true`. Catalog entry IDs and labels are authoritative for snapshot identity and presentation; provider-native runtime source metadata must not be used to infer the selected logical region or version. The selected snapshot is encoded in the `snapshot` query parameter. An invalid, missing, or non-selectable value must resolve to `catalog.defaultSnapshot`, and the resolved value must be restored in the route.

Each selected snapshot must load its manifest from `/resources/world-map/snapshots/<snapshotId>/manifest.json` and resolve each manifest node chunk relative to that snapshot base. The formal runtime contract is schema version 3 with canonical schema version 8. Asset `file` values remain resources-relative and continue to resolve through the existing World Map asset-path helper. Historical runtime source versions are opaque strings, and the frontend must accept the provider/source variants published by the versioned runtime.

Manifest and node caches, in-flight requests, loaded-node state, and offline readiness must remain isolated by snapshot identity and manifest cache key. Switching snapshots must reset active interaction state, prevent stale requests from writing into the current view, retain the current native `worldMapId` only when the new manifest contains it, and otherwise select a valid root. Refreshing or navigating browser history must restore the selected snapshot from the route.

When a link publishes `hitPath`, pointer hit testing must use that SVG path directly in the base-map coordinate system without applying `screenOrigin` translation or coordinate clamping. The existing semantic HTML button remains the keyboard and screen-reader control while pointer interaction moves to the SVG path. When `hitPath` is absent, pointer interaction falls back to `hitRect`, then to the link image bounds. `hitRect` remains available for coarse geometry, focus/button placement, tooltip anchoring, and active-target positioning.

Explicit offline readiness is tracked independently per snapshot ID and manifest `cacheKey`. Multiple catalog snapshots may be downloaded and retained for offline use at the same time; selecting, downloading, or removing one snapshot must not discard another snapshot's compatible offline data. Offline metadata is persisted per snapshot so concurrent browser contexts cannot overwrite unrelated snapshot readiness. Mutating work for the same snapshot is serialized across browser contexts, while different snapshots remain independent; a stale download, remove, or manifest synchronization must not overwrite or prune a later same-snapshot revision. Offline manifests are cached with the manifest `cacheKey` in their Cache Storage request identity, matching the revision-scoped node and image URLs. A persisted `ready` entry is trusted only after the client verifies its matching cached manifest, every manifest node chunk, and every referenced image; missing or corrupt resources downgrade only that snapshot to a resumable/non-ready state. Within one snapshot, a changed manifest `cacheKey` supersedes only that snapshot's older cached revision. World Map cache namespaces are tied to the supported runtime and canonical schema generation: known legacy and older generations are discarded when the client moves forward, while generations newer than the running client are left untouched. In-flight work for an older revision must not mark a newer revision ready.

## Rationale

World Map data now has multiple historically meaningful, provider-diverse releases. Catalog metadata is the authoritative presentation and identity boundary, while versioned v3/v8 runtime resources allow the UI to browse each release without accidentally reusing nodes, requests, pointer geometry, or offline readiness from another release.

## Acceptance Criteria

- GMS/270, TWMS/124 archived-WZ, and TWMS/236 MapleStory.IO snapshots load from their versioned v3/v8 manifests and chunks.
- The selector displays only selectable catalog entries using catalog labels; invalid or non-selectable route snapshots resolve to the catalog default.
- Snapshot changes and refresh preserve the snapshot query, reset active targets, avoid cross-snapshot node reuse, and choose a valid node/root when IDs differ.
- SVG `hitPath` interaction uses the published even-odd path geometry without `screenOrigin` translation; transparent external PNG regions do not become rectangular pointer targets, while enclosed transparent holes retain the resources-defined hit behavior.
- `hitPath: null` retains rectangular/image fallback behavior, and Tab/Enter/Space operation through the semantic HTML control remains available.
- Offline readiness is evaluated against the selected snapshot and matching manifest cache key, while multiple compatible snapshots can remain downloaded simultaneously; per-snapshot metadata survives direct reloads and concurrent tabs without clobbering unrelated entries, same-snapshot mutations are serialized across tabs, persisted ready state is rejected when any required cached manifest/node/image is missing or invalid, changing one snapshot's manifest cache key removes only that snapshot's older revision, known legacy/older schema generations are discarded without deleting future generations, and stale in-flight work cannot mark or prune a newer revision.
