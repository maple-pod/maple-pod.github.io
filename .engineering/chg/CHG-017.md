## Rationale

Physical Android testing established that both fixed-sequence and runtime-mutated MSE playback remain continuous in the background while per-track `audio.src` replacement does not. Before connecting MSE to the production queue, the player needs evidence that a bounded buffer can advance through more media than Chromium accepts in one SourceBuffer allocation, evict old segments, retain Previous semantics, reconcile future-order changes, and jump to a distant queued track without replacing the authoritative source.

## Sources

- Maintainer physical-device report after `b23b779`: runtime replacement of the buffered MSE future remained continuous and all tested controls behaved correctly.
- CHG-015 and CHG-016 established one stable MSE source across multiple independent WebM/Opus tracks and dynamic future replacement.
- The existing queue contracts in REQ-003 and REQ-004 require previous/next, random/reordered queue behavior, direct queue navigation, and standard current-track semantics.

## Changes

- Record MSE with a stable `HTMLAudioElement`/`MediaSource` identity as the accepted refactor direction for compatible source-preserved tracks while keeping the current production player unchanged.
- Add a standalone diagnostic `MsePlaybackScheduler` that maintains a bounded MSE window, fetches media only when appending it, evicts older buffered ranges, appends future tracks in sequence mode, and never replaces `audio.src` after initialization.
- Configure the diagnostic window as one previous track, the current track, and three future tracks so it exercises both backward navigation and several minutes of background-safe lookahead without loading the entire queue.
- Expand the diagnostic queue to ten low-bitrate WebM/Opus tracks so cumulative appended media exceeds the earlier one-shot SourceBuffer quota while the active buffered window remains bounded.
- Expose near-boundary stepping, Previous, Next, future reordering, and a distant queued-track jump for direct physical testing of scheduler reconciliation.

## Verification

Result: passed

- Desktop Chromium initialized the bounded window as A → B → C → D with 6.89 MB appended and one stable `blob:` source.
- Six natural boundary crossings advanced the window through G while playback stayed active; by G the active window was E → F → G → H → I, the buffered start had advanced from 0 to 492.3 seconds, and cumulative appended media reached 14.90 MB without `QuotaExceededError`.
- Reordering G's future rebuilt it as J → H → I while retaining previous/current media and the same `audio.src`; cumulative append traffic reached 22.06 MB without quota failure.
- A fresh-session direct jump from A to the initially unbuffered H rebuilt a bounded G → H → I → J window and sought to H while playback remained active and the same blob source identity was preserved.
- Previous retained the standard player semantic: when more than three seconds into a track it first sought to that track's start, and a subsequent Previous moved to the retained prior track without source replacement.
- A post-lint Chromium smoke test crossed A → B, reordered B's future into J → C → D while B remained active, kept playback unpaused, and preserved the exact same blob source URL.
- `pnpm lint`, `pnpm type-check`, and `pnpm build` passed; EF snapshot validation completed with 0 errors, 0 warnings, and 0 info diagnostics.
- Physical Android background continuity with the rolling bounded window remains intentionally pending maintainer testing; previous physical tests already validated fixed and dynamically mutated MSE timelines.
