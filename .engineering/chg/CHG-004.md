## Rationale

The design-system semantic color aliases introduced in the previous change were emitted under `:root`, while the dark theme only overrode their foundation tokens under `[color-scheme="dark"]`. CSS custom properties resolve alias values in the scope where the alias is declared, so semantic roles such as card surfaces and secondary text kept their light values even though the active foundation tokens were dark. This produced a mixed light/dark interface in production.

## Sources

- Maintainer-reported dark-mode failure on a mobile production build, reproduced in the production screenshot matrix for issue #6.
- Browser computed-style inspection of `maple-pod.github.io@11c478d`, showing dark foundation tokens alongside light semantic aliases.

## Changes

- Re-declared semantic color aliases inside the dark PikaCSS theme scope so they resolve against dark foundation tokens.
- Updated REQ-010 acceptance criteria to require theme-scoped semantic roles to remain consistent across light and dark modes.
- Added a production-CSS regression check that fails the build when the dark theme omits required semantic color variables.

## Verification

Result: passed

- `pnpm lint` passed.
- `pnpm type-check` passed.
- `pnpm build` passed and the new theme-token verification confirmed all required dark semantic color variables are emitted.
- Production preview computed styles confirmed dark semantic surface, text, border, focus, and state variables resolve to dark-theme values.
- Browser verification at a 393×852 viewport confirmed cards render with the dark surface and border palette instead of the regressed light surface.
