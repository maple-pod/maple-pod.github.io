## Rationale

Background playback has two concrete stall modes in the current player: source replacement depends on `HTMLMediaElement.autoplay` to start the next track, and a non-running Web Audio context can leave the media element logically playing while media time stops advancing. The player already has an active Media Session and should explicitly continue an established playback session while making bounded attempts to recover a recoverable audio context.

## Sources

- Maintainer report that mobile playback stops after the app remains in the background and resumes when foregrounded.
- Browser baseline instrumentation showed natural track transitions replace `audio.src` without calling `HTMLMediaElement.play()`.
- Browser control test with `audio.autoplay = false` reproduced the track-boundary failure deterministically: the next source loaded at `currentTime = 0` and remained paused.
- Browser baseline with `AudioContext.suspend()` reproduced the lifecycle symptom independently: `audio.paused` remained `false` while media time stopped advancing.
- MDN documents that browsers may ignore autoplay, including in background contexts, and recommends not depending on it to start playback.

## Changes

- Modified REQ-003 so active source transitions explicitly request playback rather than depending on autoplay, including background playback where the platform permits it.
- Made media-element playback requests observable through their Promise result and restored transition gain when a request is rejected.
- Disabled autoplay in the player path so successful continuous playback is proven to come from the explicit playback flow.
- Modified ADR-008 and the Web Audio runtime so active non-running contexts receive deduplicated resume attempts on playback preparation, context state changes, and foreground/page restoration.

## Verification

Result: passed

- Browser baseline reproduced autoplay dependence before the implementation change: with `audio.autoplay = false`, the replacement source loaded at `currentTime = 0` and remained paused because no `play()` call occurred.
- Post-change browser instrumentation confirmed the player keeps `autoplay = false` and explicitly issues `play()` for initial playback and natural source transitions; Dragon Dream → Floral Life produced `play-call` / `play-resolve` and the replacement track advanced normally.
- Explicit UI Next produced the same source-set → play-call → play-resolve sequence with autoplay disabled.
- Forced `AudioContext.suspend()` during active playback produced `suspended → running` through the new statechange recovery path; the media element remained unpaused and advanced from 13.84s to 15.06s during the observation window.
- `pnpm lint` passed.
- `pnpm type-check` passed.
- `pnpm build` and theme verification passed.
- `ef validate --scope snapshot` passed with 0 errors and 0 warnings.
- Physical long-duration Android background playback remains a device-level follow-up because browser automation cannot reproduce OS process freezing or vendor battery-management behavior.
