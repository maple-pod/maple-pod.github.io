## Context

The original player applied both persisted user volume and the short source-switch transition envelope through `HTMLAudioElement.volume`. That property is limited to 0..1, cannot apply the positive gain required by quiet catalogue outliers, and conflates independent gain responsibilities. The experimental Web Audio path demonstrated both useful loudness matching and a substantial reduction in audible track-switch discontinuities.

Phase 1 catalogue analysis measured all 1,360 source-preserved tracks. The selected -16 LUFS target with a -1 dBTP ceiling keeps 94.12% of tracks within ±1 LU of target using only static gain while peak-limiting 11.69% of the catalogue. The player must not alter source files or silently introduce dynamics processing.

## Decision

On playback preparation, supported browsers lazily route the existing media element through this Web Audio graph:

`HTMLAudioElement -> MediaElementAudioSourceNode -> normalization GainNode -> transition GainNode -> user-volume GainNode -> destination`

The graph is the default playback path whenever it can be established; its creation does not depend on loudness metadata being loaded. This keeps the transition and user-volume stages available for normal playback even while the normalization stage remains at unity. `HTMLAudioElement` remains the media source, Media Session-facing playback primitive, and fallback path rather than being replaced by an AudioBuffer-only decoder.

The normalization stage applies `10^(gainDb/20)` from the metadata-derived static gain when a current catalogue report is valid. The transition stage retains the short fade around source replacement. The user-volume stage reflects the persisted logical 0..1 volume. Mute remains a media-element mute state. Once the graph is active, `HTMLAudioElement.volume` stays at unity so user volume is not multiplied twice.

The catalogue loudness report remains a separate generated resource tied to a specific `data.json` build. It may load after catalogue data; when valid it automatically enables the normalization gain stage. Gain changes use a short AudioParam ramp to avoid introducing a discontinuity when the track gain changes. There is no persisted or user-facing normalization toggle.

No limiter, compressor, EQ, or other dynamics stage is added. If metadata loading or report validation fails, the normalization stage stays bypassed. If Web Audio is unavailable or graph creation fails, normal media-element playback remains the fallback.

## Alternatives

- Continue using `HTMLAudioElement.volume` as the normal gain path: rejected because it cannot amplify above unity, conflates gain responsibilities, and experimental use showed less continuous track switching.
- Remove `HTMLAudioElement` and decode/play tracks exclusively through Web Audio buffers: rejected because the media element remains valuable for browser media lifecycle behavior, streaming, Media Session integration, and a simple fallback when Web Audio cannot be established.
- Rewrite or normalize the audio files offline: rejected because the catalogue intentionally preserves the selected source representation and should avoid another lossy encode or asset mutation.
- Add a limiter/compressor immediately: deferred because the -16 LUFS static-gain candidate already covers most tracks without dynamics processing; peak-limited outliers can be evaluated separately.
- Keep normalization behind an Experimental toggle: rejected after production use showed a material consistency improvement and the gain graph also improved source-transition continuity.

## Consequences

- Supported playback gets independent normalization, source-transition, and user-volume gain responsibilities by default.
- Positive and negative normalization gain can be applied without changing source files.
- The media element remains present and can continue playback when the Web Audio graph cannot be established.
- Browser AudioContext lifecycle and user-gesture restrictions remain compatibility risks, especially for mobile/background playback, and require separate verification and hardening.
- The resources deployment continues to provide one generated loudness-analysis metadata file tied to a specific `data.json` build.
