## Context

The original player applied both persisted user volume and the short source-switch transition envelope through `HTMLAudioElement.volume`. That property is limited to 0..1, cannot apply the positive gain required by quiet catalogue outliers, and conflates independent gain responsibilities. The experimental Web Audio path demonstrated both useful loudness matching and a substantial reduction in audible track-switch discontinuities.

Phase 1 catalogue analysis measured all 1,360 source-preserved tracks. The selected -16 LUFS target with a -1 dBTP ceiling keeps 94.12% of tracks within ±1 LU of target using only static gain while peak-limiting 11.69% of the catalogue. The player must not alter source files or silently introduce dynamics processing.

Production Android testing then showed a separate lifecycle constraint: when `createMediaElementSource()` reroutes the media element through an `AudioContext`, mobile background interruption can stop audible playback mid-track even while the `HTMLAudioElement` remains logically unpaused and resumes when the page returns to the foreground. Background playback therefore cannot depend on a continuously running Web Audio context.

Follow-up physical Android testing of the `captureStream()` hybrid showed that the captured Web Audio foreground path produced intermittent audio and that background playback could still stop. The hybrid therefore remains useful on other supported browsers but is not a reliable Android playback path yet.

A later production MSE migration preserved one media-element source across compatible tracks and passed fixed, dynamic, and bounded diagnostic tests, but long-running physical Android use still observed an occasional production stop. The maintainer chose to return the web build to the simpler direct-source transport and expects a future Cordova/native backend for stronger platform-level background guarantees.

## Decision

For the current web backend, `HTMLAudioElement` is the authoritative source, decoder, playback clock, Media Session-facing primitive, and native background playback path. Web Audio is an optional output enhancement layered on top of that same media element rather than the owner of playback. Higher-level queue and player state depend on the playback-backend boundary in ADR-010 rather than on this concrete web primitive.

Android currently uses the native media-element path for both visible and hidden playback and does not establish `captureStream()` or an `AudioContext`. This is a reliability baseline based on physical-device results, not a claim that Android can never support an enhanced path. During this baseline, Android track switches bypass the transition envelope so source replacement does not intentionally drive the authoritative media element's native volume to zero.

The production web backend uses per-track `HTMLAudioElement.src` replacement with explicit playback requests and last-request-wins source resolution. The MSE experiments remain diagnostic evidence about Android source/session continuity but are no longer the production transport. Stronger background-lifecycle guarantees are deferred to a future native playback backend rather than adding more browser-specific queue buffering to the logical player.

On browsers that support `HTMLMediaElement.captureStream()`, a visible page may lazily establish this enhancement graph:

`HTMLAudioElement.captureStream() -> MediaStreamAudioSourceNode -> normalization GainNode -> transition GainNode -> user-volume GainNode -> destination`

The `AudioContext` uses the `playback` latency hint because the graph serves long-form music playback rather than latency-sensitive interactive audio. While enhanced output is active, the media element remains unmuted but its native `volume` is set to zero; the captured stream continues to carry the decoded media and the Web Audio graph applies normalization, transition gain, and user volume. While native output is active, the Web Audio user-volume stage is set to zero and the media element volume carries the user's logical volume and transition gain.

Output routing is fail-safe toward native media playback. A `visibilitychange` to a non-visible state synchronously selects native output before the page can be frozen. Any non-running Web Audio context also immediately selects native output. Foreground/page restoration may attempt to resume Web Audio, but the player switches back to enhanced output only after the context is confirmed `running` and a captured audio source is bound. A failed or platform-blocked resume remains non-fatal and leaves native playback active.

The captured stream remains associated with the authoritative media element across source replacements. Chromium exposes a new captured audio track for a replacement media source, so the output controller binds a new `MediaStreamAudioSourceNode` to the existing gain graph and stops/removes the previous captured track rather than rebuilding the `AudioContext` or transferring playback-clock ownership.

The normalization stage applies `10^(gainDb/20)` from the metadata-derived static gain when a current catalogue report is valid and enhanced output is active. Gain changes use a short AudioParam ramp to avoid introducing a discontinuity when the track gain changes. There is no persisted or user-facing normalization toggle. Native fallback intentionally bypasses runtime Web Audio normalization until a separate native-safe normalization mechanism is adopted.

No limiter, compressor, EQ, or other dynamics stage is added. If `captureStream()` or Web Audio is unavailable, graph creation fails, the page is hidden, or the context is interrupted/suspended, normal media-element playback remains available without source replacement or playback-position transfer.

## Alternatives

- Keep `createMediaElementSource()` as the default output route and repeatedly call `AudioContext.resume()`: rejected because physical Android testing showed that a background-interrupted context can stop audible playback mid-track while the media element remains logically active.
- Keep the `captureStream()` enhancement enabled on Android while relying on visibility handoff: rejected for the current baseline because physical-device testing showed intermittent foreground audio and background interruption.
- Disable Web Audio permanently on Android: not decided; the current native-only Android route is a diagnostic baseline while native-safe normalization and other enhancement options are evaluated.
- Remove `HTMLAudioElement` and decode/play tracks exclusively through Web Audio buffers: rejected because the media element provides browser media lifecycle behavior, streaming, Media Session integration, and the native background path.
- Keep bounded MSE scheduling as the production web transport: deferred after long-running physical Android use still observed an occasional stop and the maintainer preferred a simpler web backend plus a future native transport. The MSE diagnostics remain useful research evidence.
- Rewrite or normalize the audio files offline immediately: deferred because the catalogue intentionally preserves source representations; native-safe asset normalization is evaluated separately.
- Add a limiter/compressor immediately: deferred because the -16 LUFS static-gain candidate already covers most tracks without dynamics processing; peak-limited outliers can be evaluated separately.

## Consequences

- Background playback no longer depends on a running `AudioContext`; the media element can continue advancing and producing native audio while Web Audio is suspended or interrupted.
- Visible supported playback retains independent normalization, source-transition, and user-volume gain responsibilities through Web Audio.
- Runtime loudness normalization may be temporarily absent while native fallback is active; playback continuity takes priority until asset/native-path normalization is added.
- Unsupported `captureStream()` environments use native media-element playback without creating an AudioContext.
- Android currently follows the same native-only behavior even when `captureStream()` exists, so Android testing is isolated from capture/Web Audio lifecycle effects. Its track-switch transition is also bypassed during this diagnostic baseline, trading click suppression for a cleaner media-session continuity test.
- Source changes require captured-track rebinding and explicit cleanup of stale tracks, while the authoritative media element and AudioContext remain stable.
- Browser lifecycle signals remain advisory, but output failure now degrades to native playback rather than silence.
- The resources deployment continues to provide one generated loudness-analysis metadata file tied to a specific `data.json` build.
- Background-playback diagnosis may use a static single-source native `<audio controls>` page that does not load the application runtime, replace media sources, or configure Media Session, so browser/OS lifecycle behavior can be isolated from player logic.
- Physical Android testing of that fixed single-file diagnostic remained continuous in the background, unlike normal per-track source replacement. The next diagnostic therefore keeps one `HTMLAudioElement` source identity while using Media Source Extensions to append multiple WebM/Opus tracks into one sequence-mode timeline, isolating source/session continuity from the fact that the catalogue is stored as separate tracks.
- Physical Android testing of the five-track MSE sequence also remained continuous across track boundaries. A follow-up diagnostic may mutate only the not-yet-played MSE future by removing buffered entries and appending a replacement sequence at the same timeline boundary while preserving the same `HTMLAudioElement` and blob source identity; this tests whether dynamic queue changes can retain the background-session continuity demonstrated by the fixed MSE sequence.
- Physical Android testing of runtime MSE future replacement also remained continuous and correct. Bounded scheduling is therefore the next integration constraint: keep enough future media buffered to survive background JavaScript suspension, retain limited previous media for navigation, evict older segments before SourceBuffer quota pressure, and reconcile queue changes without replacing the media element source. The exact production buffer horizon remains to be selected from further measurements rather than fixed by the diagnostic window size.

- The web backend again replaces `HTMLAudioElement.src` per track and accepts the known browser/OS background-continuity limitation of that transport.
- The production player no longer depends on MSE buffering or a global MSE timeline; those experiments remain isolated diagnostics rather than product state.
- Queue and control orchestration are separated from the concrete web transport by ADR-010 so a future Cordova/native backend can replace the playback engine without duplicating player state.
