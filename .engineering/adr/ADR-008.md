## Context

The current player applies both the persisted user volume and the short source-switch transition envelope through `HTMLAudioElement.volume`. That property is limited to 0..1, so it cannot apply the positive gain required by quiet catalogue outliers, and it conflates independent gain responsibilities.

Phase 1 catalogue analysis measured all 1,360 source-preserved tracks. The first experimental setting uses -16 LUFS with a -1 dBTP ceiling because it keeps 94.12% of tracks within ±1 LU of target using only static gain while peak-limiting 11.69% of the catalogue. The feature must not alter source files or silently introduce dynamics processing.

## Decision

When the experimental setting is enabled, route the existing media element through a lazily-created Web Audio graph:

`HTMLAudioElement -> MediaElementAudioSourceNode -> normalization GainNode -> transition GainNode -> user-volume GainNode -> destination`

The normalization stage applies `10^(gainDb/20)` from the metadata-derived static gain. The transition stage retains the existing short fade around source replacement. The user-volume stage reflects the persisted logical 0..1 volume. Mute remains a media-element mute state. Once the graph is active, `HTMLAudioElement.volume` stays at unity so user volume is not multiplied twice.

The setting is persisted but defaults off. Its catalogue loudness report is a separate resource generated by the resources pipeline and is fetched lazily when normalization is enabled. The report is accepted only when its resource build identifier and catalogue counts match the currently loaded resources. Gain changes use a short AudioParam ramp to avoid introducing a discontinuity when the setting or track gain changes.

The experimental version does not add a limiter, compressor, EQ, or other dynamics stage. If metadata loading, report validation, or Web Audio graph creation fails, normalization remains bypassed and normal media-element playback continues.

## Alternatives

- Continue using `HTMLAudioElement.volume`: rejected because it cannot amplify above unity and cannot cleanly separate user, transition, and normalization gain.
- Rewrite or normalize the audio files offline: rejected because the catalogue intentionally preserves the selected source representation and should avoid another lossy encode or asset mutation.
- Add a limiter/compressor immediately: deferred because the -16 LUFS static-gain candidate already covers most tracks without dynamics processing, and real experimental use should establish whether peak-limited outliers justify an additional stage.
- Hide the experiment behind a URL flag or one-off A/B prototype: rejected in favor of a normal, persisted Experimental setting that users can opt into and disable at any time.

## Consequences

- Positive and negative normalization gain can be applied without changing the source files.
- User volume, source-transition gain, and normalization gain become independent responsibilities once the experimental graph is active.
- Browser AudioContext lifecycle and user-gesture restrictions must be handled so enabling the experiment does not create silent playback.
- The resources deployment gains one generated loudness-analysis metadata file tied to a specific `data.json` build.
- A later decision is still required before removing the Experimental label, making normalization default-on, or adding peak-limiting/dynamics processing.
