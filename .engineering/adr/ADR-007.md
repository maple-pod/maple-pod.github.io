## Context

Maple Pod already has a recognizable visual system: MapleStory artwork supplies atmosphere, translucent glass-like cards provide structure, a restrained red accent carries actions, and light/dark themes are implemented through PikaCSS tokens. The implementation also has local `Ui*` wrappers over reka-ui. However, system rules beyond the color palette are spread across PikaCSS shortcuts and component literals, and there is no durable design document defining typography, spacing, shape, motion, focus, responsive behavior, or reusable component contracts.

## Decision

Preserve the incumbent visual identity and formalize it as a design system rather than redesigning the application. Root `DESIGN.md` is the human- and agent-readable design contract, while PikaCSS design tokens and local `Ui*` primitives are the executable enforcement layer.

The system is organized into foundation tokens (color, spacing, typography, radius, elevation/blur, motion, and control size), semantic roles (text, surfaces, borders, actions, states, and focus), reusable component contracts, and responsive/interaction patterns. Stable repeated literals should move behind meaningful tokens or component contracts when that reduces drift; values should not be tokenized mechanically when they are genuinely local.

PikaCSS strict design-token governance is introduced incrementally: color is governed at warning severity first, with semantic aliases explicitly typed as color tokens; dimension and duration governance remain off until incumbent spacing and motion usages can migrate without non-actionable diagnostic noise. A governed type may advance to error severity only after incumbent usages comply. Component-local responsiveness should prefer container queries when behavior depends on the component's available width rather than the viewport.

The working creative north star is **Maple Memory Player**: MapleStory scenery and music carry nostalgia and atmosphere, while the player interface stays modern, quiet, clear, and subordinate to the content.

## Alternatives

- Keep visual conventions implicit in `pika.config.ts` and component code. This has lower immediate documentation cost but leaves future UI work and agents without a complete source of design intent.
- Adopt a styled third-party component system. This would duplicate or replace the existing PikaCSS/reka-ui architecture and would make preservation of Maple Pod's incumbent identity harder.
- Redesign the visual identity before formalizing it. This was rejected because the current artwork/glass/red-accent composition already has a coherent identity; the immediate problem is consistency and governance, not lack of direction.

## Consequences

- New UI work has an explicit contract for visual roles, component behavior, accessibility, focus, motion, and responsive adaptation.
- PikaCSS remains the styling engine defined by ADR-003, and reka-ui remains the headless behavior layer defined by ADR-004.
- `DESIGN.md`, PikaCSS tokens, and reusable `Ui*` primitives must remain aligned as the system evolves.
- Design-token strictness is intentionally staged so existing UI can migrate without a disruptive all-at-once rewrite.
- The design system preserves the current aesthetic instead of using systemization as justification for unrelated visual redesign.
