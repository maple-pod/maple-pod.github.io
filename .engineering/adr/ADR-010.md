## Context

Maple Pod's queue, repeat, shuffle, history, persisted preferences, and UI semantics are independent of how a track is physically played. The production MSE experiment temporarily pulled transport concerns such as global media timelines and buffered queue reconciliation into `useAudioPlayer`, making that orchestration depend on a browser-specific playback mechanism. The maintainer expects a future Cordova/native application shell and wants that migration to replace the playback engine without rewriting the existing player state and UI.

## Decision

Define a narrow `AudioPlaybackBackend` contract at the transport boundary. `useAudioPlayer` owns queue interaction, source-resolution ordering, repeat behavior, persisted preferences, and logical current-track state. A backend owns the concrete transport and exposes only the capabilities the orchestration needs: load/unload, play/pause, current time and duration, volume/mute/loop, readiness/error/waiting state, ended and seeked notifications, and optional normalization/output-transition controls.

The current default backend is `useHtmlAudioPlaybackBackend`, which directly owns one `HTMLAudioElement` and its web-specific media state. `useAudioPlayer` accepts a backend factory and defaults directly to that HTML backend; there is no additional default-backend wrapper. Code above this boundary must not require a concrete DOM media element or MSE object. Web-only output processing may remain as a private helper beneath the HTML backend without becoming part of the logical player architecture.

A future Cordova/native backend may implement the same contract with a native playback plugin. This decision does not select a Cordova plugin, native audio library, or native media-session implementation in advance.

## Alternatives

- Keep `HTMLAudioElement` directly embedded in `useAudioPlayer`: rejected because transport-specific DOM access would force future native playback to rewrite player orchestration.
- Keep the production MSE scheduler as the abstraction boundary: rejected because MSE is a browser transport strategy, not the logical player contract, and long-running production testing still observed an occasional stop.
- Move queue and repeat semantics into each playback backend: rejected because those are product semantics that should remain identical across web and native transports.
- Define a broad generic media-plugin framework now: rejected because only audio playback has a concrete replacement requirement; the backend contract stays limited to capabilities already used by the player.

## Consequences

- The web build continues to use the existing `HTMLAudioElement` behavior behind an adapter while upper player code becomes transport-agnostic.
- A future native backend can reuse queue, controls, persistence, history, UI, and logical time semantics without emulating an `HTMLAudioElement`.
- Browser Media Session integration consumes backend-independent player state and seek notifications rather than a DOM media element directly.
- Backend implementations may differ in optional normalization/output capabilities; unsupported capabilities can be reported through the existing support state instead of leaking transport details upward.
- Adding a native backend may still require runtime-specific system-media integration, but it does not require a second queue or player state machine.
