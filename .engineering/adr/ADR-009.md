## Context

The canonical World Map document is too large for normal frontend entry and navigation, and the resources set now contains multiple historical GMS/TWMS snapshots from different source providers. The runtime therefore needs both progressive loading and an explicit snapshot identity boundary. Resources publish a schema-v1 catalog plus versioned schema-v3 manifests and node chunks with canonical schema version 8. The old unversioned GMS/270 schema-v1/canonical-v6 alias remains a rollout compatibility resource, not the formal multi-snapshot UI contract.

## Decision

Use `/resources/world-map/catalog.json` as the frontend entry point and let its selectable entry ID choose `/resources/world-map/snapshots/<snapshotId>/manifest.json`. Resolve node chunks relative to that snapshot base using schema-v3 chunks shaped as `{ schemaVersion, canonicalSchemaVersion, worldMapId, node }`. Keep published asset paths resources-relative. Runtime source metadata records provenance, while catalog `region`, `version`, `id`, and `label` define UI snapshot identity.

Cache runtime data with snapshot identity and manifest `cacheKey` so manifests, nodes, requests, loaded state, and offline readiness cannot leak across snapshots or manifest revisions. Manifest, node, and image offline cache identities include the manifest cache key as a revision discriminator. Compatible snapshots are independent offline units and may coexist in Cache Storage; selecting or downloading one snapshot does not invalidate another. Offline metadata is stored as an independent record per snapshot, which prevents concurrent tabs working on different snapshots from replacing one aggregate registry. Mutating operations for the same snapshot are serialized across browser contexts, while different snapshots can proceed independently; local request-generation guards prevent stale manifest requests or fire-and-forget synchronization from committing after a newer request. Persisted ready records are revalidated against the cached manifest, every node chunk, and all referenced images before the UI reports them ready. When a manifest `cacheKey` changes, only that snapshot's older revision is pruned. Cache names include the supported runtime and canonical schema generation. Startup cleanup removes known legacy and older World Map cache/metadata generations but deliberately preserves generations newer than the running client so an older open tab cannot delete data created by a newer application version. Explicit offline preparation caches each requested snapshot's manifest, every node chunk, and every referenced image.

Use resources-published `hitPath` geometry for exact pointer hit testing when present. The path is already expressed in base-map pixel coordinates and is not translated by `screenOrigin`. Keep HTML buttons as semantic keyboard/screen-reader controls, and retain `hitRect` then link-image bounds as pointer fallbacks when no path exists.

The unversioned `/resources/world-map/manifest.json` and `/resources/world-map/nodes/*` aliases remain resources-side rollback/compatibility artifacts only; the migrated UI does not depend on them.

## Alternatives

- Continue using the unversioned GMS/270 schema-v1 runtime and infer versions from runtime provenance: rejected because it cannot represent the catalog's selectable historical snapshots and provider-native regions are not the logical UI identity.
- Fetch and parse the canonical full `world-maps.json` document on World Map entry: rejected because it defeats progressive startup and transfers the large canonical payload for routine browsing.
- Use rectangular HTML controls for all pointer interaction: rejected because transparent regions of published link PNGs become false-positive hit targets; exact alpha-derived `hitPath` geometry is already available in the runtime.
- Store complete map JSON and image blobs in localforage: rejected because Cache Storage can serve the existing versioned resource URLs offline without duplicating resource blobs.

## Consequences

- Initial and navigational requests remain bounded to the catalog, selected manifest, active node chunks, and active-node assets.
- Historical GMS/TWMS snapshots can be deep-linked and switched without reusing incompatible node state.
- Runtime provenance remains inspectable without coupling UI identity to provider-native region/version conventions.
- Pointer interaction matches the published image silhouette while keyboard and screen-reader semantics remain on ordinary HTML controls.
- Offline preparation may consume substantial storage because multiple compatible snapshots can coexist. Old revisions are pruned per snapshot; known legacy and older schema generations are removed instead of being treated as reusable, while future generations are preserved for forward coexistence with newer clients.
