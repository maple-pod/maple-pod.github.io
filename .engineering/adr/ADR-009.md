## Context

The canonical World Map document is too large for normal frontend entry and navigation. The resources runtime now provides a concrete progressive contract: a schema-v1 manifest with canonical schema version metadata and one compact schema-v1 chunk per native world-map node. The World Map also needs explicit full offline availability without changing normal lazy navigation.

## Decision

Use `/resources/world-map/manifest.json` as the runtime index. Its schema-v1 `nodes` entries identify each node with `worldMapId`, `chunk`, canonical fallback labels, parent/child/link relationships, and missing-link metadata; localization remains in the node chunk. Fetch node data through the manifest's `chunk` path using schema-v1 chunks shaped as `{ schemaVersion, canonicalSchemaVersion, worldMapId, node }`. Cache loaded nodes in memory for normal navigation.

For explicit full offline use, use Cache Storage for the manifest, every node chunk, and every image referenced by those chunks. Use `manifest.cacheKey` as the readiness identity, keep only lightweight status metadata outside Cache Storage, bound concurrent work, support cancellation/resume/remove, and mark a cache key ready only after every required resource succeeds. Normal World Map navigation does not initiate this full download.

## Alternatives

- Fetch and parse the canonical full `world-maps.json` document on World Map entry: rejected because it defeats progressive startup and transfers the large canonical payload for routine browsing.
- Store complete map JSON and image blobs in localforage: rejected because Cache Storage can serve the existing resource URLs offline without duplicating resource blobs.
- Download all map resources during ordinary navigation: rejected because full offline preparation is an explicit user action and must not change progressive browsing behavior.

## Consequences

- Initial and navigational requests remain bounded to the manifest, active node chunks, and active-node assets; unloaded labels use canonical manifest fallbacks.
- Runtime localization and node relationships stay authoritative in the chunks while the manifest remains a compact index suitable for enumeration.
- Offline preparation may consume substantial storage, but it is resumable, cancellable, removable, and versioned by `cacheKey`; partial caches are not presented as fully ready.
- Cache Storage URL reuse lets the service worker and normal fetches share offline resources, while stale readiness metadata is ignored.
